## EDSL Object Save/Load

**All EDSL objects** (`Results`, `AgentList`, `Survey`, `ScenarioList`, Jobs, etc.) should be persisted with the EDSL `.ep` file accessor. Always use `.git.save()` / `.git.load()` instead of manual JSON serialization or legacy compressed object files.

| Wrong | Right | Notes |
|-------|-------|-------|
| `json.dump(obj.to_dict(), f)` | `obj.git.save("path/to/object.ep")` | Built-in EDSL file format preserves object metadata |
| `Class.from_dict(json.load(f))` | `Class.git.load("path/to/object.ep")` | Use the `.ep` file produced by EDSL |
| Custom `save_json` / `load_json` helpers | `obj.git.save()` / `Class.git.load()` | Don't reinvent what EDSL provides |

```python
# Save any EDSL object
agent_list.git.save("edsl_jobs/job_a/agent_list.ep")
survey.git.save("edsl_jobs/job_a/survey.ep")
scenario_list.git.save("edsl_jobs/job_a/scenario_list.ep")
job.git.save("edsl_jobs/job_a/jobs.ep")

# Results are generated by the CLI from jobs.ep
#   ep run edsl_jobs/job_a/jobs.ep --output data/results.ep

# Load EDSL objects in substantive Python construction or analysis code
from edsl import AgentList, Survey
agent_list = AgentList.git.load("edsl_jobs/job_a/agent_list.ep")
survey = Survey.git.load("edsl_jobs/job_a/survey.ep")
```

**Always keep the `results.ep` file from every paid run** — it contains full provenance (prompts, raw responses, costs). Extract data from the saved Results rather than discarding them.

## CLI-first routine operations

Use `ep` for object lifecycle, execution, validation, routine inspection,
selection, export, costs, and deployment. Use Python for object construction and
substantive analysis, such as statistics, reshaping, modeling, and plotting.

Do not load a Results object in Python merely to discover columns, print rows,
extract values, or export CSV. Use the supported compatibility surface:

```bash
ep results summary data/results.ep
ep results columns --file data/results.ep
ep results head data/results.ep \
  --column answer.q1 \
  --column scenario.topic \
  --rows 5
ep results values data/results.ep --column answer.q1
ep results export data/results.ep --format csv --output data/results.csv
```

If a later analysis genuinely needs a `Results` object, load it at the start of
an analysis script. That is substantive Python and remains appropriate.

## Results loading in analysis code

| Wrong | Right | Notes |
|-------|-------|-------|
| `Results.from_file(...)` | `Results.git.load("data/results.ep")` | `from_file` does not exist |
| `Results.from_disk(...)` | `Results.git.load("data/results.ep")` | `from_disk` often fails with zip format errors |
| `Results.load("data/results")` | `Results.git.load("data/results.ep")` | Use the `.ep` results file |
| `results[0]['scenario.field']` | `results[0].sub_dicts['scenario']['field']` | Dot-separated keys raise KeyError on individual Results |

For previews, use `ep results head`; never write a Python preview or index an
individual Result with dot-separated strings.

## Agent Creation

| Wrong | Right | Notes |
|-------|-------|-------|
| `Agent(traits={"name": "Alice"})` | `Agent(name="Alice", traits={...})` | `name` is reserved; putting it in traits raises `AgentNameError` |

When loading from a DataFrame or CSV with a "name" column, use `name_field`:
```python
AgentList.from_source(data, name_field="name")
```

## Jinja2 Template Syntax in Question Text

EDSL parses all question text through Jinja2 to extract template parameters. **Never use `{{` or `}}` in question text, option text, or instruction text** unless you intend an EDSL template variable (like `{{ scenario.field }}`).

Common mistake: writing JSON examples, dict literals, or format specifications inside a prompt string:

```python
# WRONG — Jinja2 will try to evaluate {{ "key": "value" }} and crash
q = QuestionFreeText(
    question_text="Rate this using {{ key: value }} format",
    question_name="rating"
)
# TemplateSyntaxError: expected token 'end of print statement', got ':'

# RIGHT — escape curly braces by doubling them in a raw string or avoid them entirely
q = QuestionFreeText(
    question_text='Rate this using the format "key: value"',
    question_name="rating"
)
```

**Never use f-strings to build question text.** F-strings use `{variable}` syntax which conflicts with EDSL's `{{ scenario.field }}` Jinja2 templates. The f-string will try to interpolate `{scenario.field}` as a Python variable (and fail), or if you double the braces to escape for the f-string, the result won't be a valid EDSL template. Always use plain strings with EDSL template variables:

```python
# WRONG — f-string conflicts with EDSL template syntax
question_text = f"What do you think about {{ scenario.topic }}?"  # produces literal {{ }}
question_text = f"What do you think about {scenario.topic}?"      # NameError at build time

# RIGHT — plain string, EDSL handles the template substitution
question_text = "What do you think about {{ scenario.topic }}?"
```

This applies to **all** question types and to `Instruction` text. If you need literal curly braces in output format instructions, describe the format in words or use parentheses/brackets instead.

### Jinja `{% if %}` control blocks work — mind undefined variables

Jinja `{% if %}` / `{% for %}` control blocks **do** work in question text, and they are the right tool for varying a question's wording by a prior answer (e.g. showing each respondent the question in their chosen language). EDSL scans control blocks for template variables, so a variable used only inside `{% if language.answer == 'Spanish' %}` is still detected as a parameter and its prior answer is piped in before rendering — in both `.run()` and humanize. See **skill:edsl-surveys** ("Jinja if/then for per-answer wording") for the pattern.

The one caveat is EDSL's `PreserveUndefined` policy: an **undefined** variable is preserved verbatim as `{{ ... }}` when printed, but inside a `{% if %}` it evaluates as **falsy** rather than erroring. So a **typo'd or not-yet-answered** variable silently takes the else-branch with no warning. Guard against it:

- Reference only prior answers that actually exist and precede this question — check the exact `question_name` (a misspelling like `langauge.answer` fails silently).
- Cover every case with an explicit `{% else %}` so a fall-through is intentional, not accidental.
- Preview the rendered text (see the live test link in **skill:edsl-human-survey**) to confirm each branch shows.

## Survey Construction

**`add_instruction()` has no `index` parameter.** Unlike `add_question(q, index=N)`, instructions are always appended in order.

**Scenario fields must appear in question text, not instructions.** EDSL's `JobsCompatibilityError` only validates `question_text` for `{{ scenario.field }}` references. Putting a scenario reference only in an `Instruction` will not satisfy the check.

## QuestionCheckBoxWithOther Write-Ins

Checkbox answers are stored as Python lists — `['Civil War', 'World War II']` — so index and iterate them directly.

`QuestionCheckBoxWithOther` subclasses `QuestionCheckBox` and returns the same list. Its write-ins are ordinary members of that list, prefixed with `other_option_text` — `['Email', 'Other: Community forum']` — so splitting predefined options from write-ins is a string check on the items, not a separate field.

## Survey.loop_over Naming Collisions

Two names worth keeping straight: `scenario_list_method="loop"` in `humanize()` repeats the whole survey per scenario, and `Question.loop(scenario_list)` expands a design-time list — neither is `Survey.loop_over`. For `loop_over` itself — `None`-padded columns, silent `max_items` truncation, which fields get `{{ item }}` substituted — see **skill:edsl-surveys** (`references/survey-reference.md`, "Constraints and gotchas"), which owns that list.

## ScenarioList.append() Is a No-Op

`ScenarioList.append()` does **not** modify the list in place. It silently does nothing. Always build a plain Python list first, then pass it to the constructor:

| Wrong | Right | Notes |
|-------|-------|-------|
| `sl = ScenarioList(); sl.append(Scenario({...}))` | `sl = ScenarioList([Scenario({...})])` | `.append()` is a no-op |

```python
# Wrong — scenarios will be empty
scenarios = ScenarioList()
for item in data:
    scenarios.append(Scenario({"field": item}))  # does nothing!

# Right — build a list, then wrap
scenario_list = []
for item in data:
    scenario_list.append(Scenario({"field": item}))
scenarios = ScenarioList(scenario_list)
```

## FileStore Images in Scenarios

When using `FileStore` to pass images to multimodal models, use `Scenario.from_image()` to create the scenario. Do **not** manually construct `FileStore` objects and put them in scenario dicts — this can cause the image to be serialized as a dict repr instead of being rendered as actual image content.

| Wrong | Right | Notes |
|-------|-------|-------|
| `Scenario({"img": FileStore(path="photo.png")})` | `Scenario.from_image("photo.png")` | Manual FileStore may serialize as dict |

To add extra fields alongside the image:

```python
s = Scenario.from_image("photo.png")
img_key = list(s.keys())[0]  # e.g., "photo"
scenario = Scenario({
    "my_image": s[img_key],
    "label": "some label",
    "description": "some description",
})
```

### Images Must Be Passed to Every Question

**LLMs have no cross-question memory of scenario content by default.** If you pass an image via `{{ scenario.my_image }}` in Q1, the image is **not** automatically available in Q2, Q3, etc. You must include the template variable in **every question** that needs the image.

| Wrong | Right | Notes |
|-------|-------|-------|
| Pass `{{ scenario.image }}` only in Q1, assume it persists | Pass `{{ scenario.image }}` in Q1, Q2, Q3, ... every question that needs it | No implicit memory |
| Use `set_full_memory_mode()` to work around this | Just pass the scenario variable in each question text | Memory modes don't provide scenario content, only prior Q&A pairs |

```python
# WRONG — Q2 and Q3 won't see the image
q1 = QuestionFreeText(
    question_name="describe",
    question_text="Describe this image: {{ scenario.image }}"
)
q2 = QuestionMultipleChoice(
    question_name="category",
    question_text="What category is this?",  # ❌ image not passed
    question_options=["A", "B", "C"]
)

# RIGHT — every question gets the image
q1 = QuestionFreeText(
    question_name="describe",
    question_text="Describe this image: {{ scenario.image }}"
)
q2 = QuestionMultipleChoice(
    question_name="category",
    question_text="Looking at this image: {{ scenario.image }}\n\nWhat category is this?",  # ✅
    question_options=["A", "B", "C"]
)
```

This applies to **all scenario fields**, not just images — but images are the most common place this causes confusion because users intuitively expect visual context to persist across questions.

**Important:** Use the EDSL revision owned by the ep-agent runtime. Do not
install, upgrade, or replace EDSL during a study; if FileStore rendering fails,
report the environment problem rather than changing the sandbox dependency.

## Empty Collections Break Job Chaining

Calling `.by()` with an empty `ScenarioList` or `AgentList` raises `IndexError`. Guard:

```python
job = survey
if len(scenario_list) > 0:
    job = job.by(scenario_list)
if len(agent_list) > 0:
    job = job.by(agent_list)
job = job.by(model_list)
```

## Cost Estimation

Use the CLI to estimate cost **before** running a saved `jobs.ep`. See `skill:edsl-surveys-cost` for the full reference including token overrides, pilot calibration, and skip-logic weights.

```bash
ep jobs cost edsl_jobs/job_a/jobs.ep
```

This fetches live prices from Expected Parrot and estimates based on prompt token counts. Use it to satisfy the "no silent spending" constraint — show the estimate to the user before running `ep run`.

After a run, get actual cost:
```bash
ep results cost data/results.ep
```

## Model Construction Requires `service_name`

When creating a `Model`, always specify `service_name` so EDSL knows which provider to query. Without it, EDSL searches only cached/test models and will fail to find real models.

```python
from edsl import Model, ModelList

# Model names below are placeholders. Confirm current ones with
# `ep models` — see skill:workflow-model-selection.
OPENAI_MODEL, ANTHROPIC_MODEL = "<openai-model>", "<anthropic-model>"

# WRONG — will fail with "Model not found in any service"
model = Model(OPENAI_MODEL)

# RIGHT — specify the provider
model = Model(OPENAI_MODEL, service_name="openai")

# Building a ModelList
model_list = ModelList([
    Model(OPENAI_MODEL, service_name="openai"),
    Model(ANTHROPIC_MODEL, service_name="anthropic"),
])
```

Also note: `edsl.config.CONFIG` is not a dict. Do not call `dict(CONFIG)` — it will raise `ValueError`. Use `CONFIG.show()` or access individual keys instead.

## Listing Models: Use `ep models`

Use the CLI rather than importing `Coop` or writing an inline Python filter:

```bash
ep models --service openai --sort input-price
ep models --vision --sort input-price
ep models --search gpt
```

Run `ep models --help` for the supported filters. Do not replace this command
with an inline Python import or API call.

## EDSL Caching in Optimization Loops (GEPA)

When EDSL is used as the backend for an optimization framework like GEPA, **all LLM calls go through `.run()` which caches by default**. This causes two problems in iterative optimization:

1. **Reflection/mutation calls return identical text every iteration** — the optimizer proposes the same mutation repeatedly, stalling progress.
2. **Evaluation calls return identical scores** — if your evaluator uses an EDSL survey panel, scores are deterministic even when you want stochastic variation.

**Fix**: Pass `fresh=True` to any `.run()` call inside an optimization loop where you need fresh responses:

```python
# In a GEPA evaluator function
results = survey.by(agents).by(model).run(fresh=True)
```

The `expectedparrot/gepa` EDSL-backend fork now handles this automatically for reflection/refiner LMs. But custom evaluators that call `.run()` must pass `fresh=True` themselves. See also `skill:methods-prompt-optimization`.

## Key `ep run` Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `--remote_inference_description` | `None` | Label for the job in the remote-inference queue. **Always pass on every run** (see below) |
| `--results_description` | `None` | Label stored on the saved Results object. **Always pass on every run**, set to the same string as `remote_inference_description` |
| `--n` | `1` | Number of independent runs per interview |
| `--fresh` | `False` | If passed, ignore cache and generate new results |
| `--progress` | `False` | Show a progress bar |
| `--local` | `False` | Optional opt-out from default remote inference; use only for local smoke tests/debugging |
| `--background` | `False` | Submit a remote job and return immediately |
| `--wait` | `False` | With `--background`, wait for completion so `--output` can be written |

**Always pass both `--remote_inference_description` and `--results_description` on every `ep run` — preview, sample, and full alike — set to the same string** — they keep the job traceable across the queue and the saved results. Full rule → `skill:edsl-surveys` — "Running a survey — labeling the job".

**`cache=False` does not exist.** To bypass the cache, use `fresh=True`. Using `cache=False` will raise an error.

## Repeated Sampling with `ep run --n N`

`ep run` accepts `--n` to run the same job multiple times independently. Each run is a fresh API call with its own sampling — useful for measuring empirical response frequencies or estimating variance.

```bash
# Run each (model, agent, scenario, question) combination 50 times
ep run edsl_jobs/job_a/jobs.ep --n 50 --output data/results.ep
```

The returned `Results` object contains all `n` runs. For a job with 8 questions and 2 models, `n=50` produces `8 × 2 × 50 = 800` result rows.

**Cost estimation with `n`**: `estimate_remote_job_cost()` estimates the cost for a single run. Multiply by `n` to get the total:

```python
estimate = job.estimate_remote_job_cost()
total = estimate.total_cost_usd * n
print(f"Estimated cost for n={n}: ${total:.4f}")
```

**Format compliance at high temperature**: When using `temperature=1` with `use_code=True` for repeated sampling, some models frequently produce unparseable responses (e.g., `"0: Dog"` instead of `"0"`), resulting in `None` answers. This varies by model and is worth spot-checking on a few cases before a full run — plan for either retry logic or a larger `n` to compensate if you see it.

**Analyzing repeated samples**: Filter out `None` answers and compute frequencies over valid responses only:

```python
for result in results:
    answer = result["answer"]["my_question"]
    if answer is not None:
        # count this response
```

## FileStore Push/Overwrite

**`fs.push(force=True)` is accepted but has no effect** — the `force` parameter is not passed through internally. To overwrite an existing alias, delete the old object first, then re-push:

```python
from edsl import Coop, FileStore

coop = Coop()
# Build alias URL dynamically (works on production and test servers)
username = coop.get_profile()["username"]
alias_url = f"{coop.url}/content/{username}/my-alias"
coop.delete(alias_url)
# Push new version
fs = FileStore('writeup/report.html')
info = fs.push(alias='my-alias', visibility='unlisted')
```

| Wrong | Right | Notes |
|-------|-------|-------|
| `fs.push(alias='x', force=True)` | Delete then re-push | `force` param is a no-op |
| `coop.list(object_type="file_store")` | N/A — not listable | `file_store` is not a valid type for `coop.list()` |

**`Coop.list()` does not support `object_type="file_store"`.** FileStore objects are not listable via `Coop.list()`. To manage them, use `FileStore.push()` and `Coop.delete()` directly.

## Working Directory Discipline

Shell state (including cwd) is **not preserved** between Bash tool calls. When running commands that depend on being in a specific directory (e.g., `bewley` or `make`), always `cd` with an absolute path at the start of each Bash call:

```bash
cd /absolute/path/to/study_root && make writeup/report.html
```

Define a root variable early and reuse it:
```bash
STUDY_ROOT="/absolute/path/to/sessions/topic_foo/study_a"
cd "$STUDY_ROOT" && make writeup/report.html
```

## API Timeouts on Large Jobs

The default API timeout (10s) is too short for pushing large objects or running big jobs. Set the environment variable before running:

```bash
export EDSL_API_TIMEOUT=120
```

For very large scenario lists (500+), consider batching.

## PDF Generation

Pandoc with `pdflatex` cannot handle emoji or unusual Unicode. Always use:

```bash
cd writeup && pandoc report.md -o report.pdf --pdf-engine=xelatex --include-in-header=report_header.tex --lua-filter=fix-table-widths.lua
```

And never put emoji in `writeup/report.md`.

## Blockquote Lines Starting with Square Brackets

Pandoc parses `> [text]: "..."` as a **link reference definition**, not as a blockquote. The line silently vanishes from the rendered HTML and PDF, producing an empty blockquote with only the green left-border visible.

| Wrong | Right | Notes |
|-------|-------|-------|
| `> [Agent type]: "quote"` | `> **Agent type:** "quote"` | Brackets + colon = link ref definition |
| `> [Rescue, prior owner]: "I..."` | `> **Rescue, prior owner:** "I..."` | Use bold for attributions |

This is especially common when attributing verbatim agent responses in the Results section. Always use **bold** instead of brackets for blockquote attributions.

## File Path Resolution in Job Scripts

Scripts in `edsl_jobs/job_a/` need to save results to the study root's `data/` directory. Use `Path(__file__)` to resolve correctly:

```python
from pathlib import Path
_STUDY_ROOT = Path(__file__).resolve().parent.parent.parent
output = _STUDY_ROOT / "data" / "results"
```

## Matplotlib: ax.text() with categorical horizontal bar axes

When a `barh` chart uses string labels on the y-axis (e.g., any Likert stacked chart), passing a numeric `0` as the y-coordinate to `ax.text()` silently places all annotations at the first category — they overlap and look like a single row is labeled while all others are blank.

Always pass the category label string as the y-coordinate:

```python
# WRONG — all text collapses to first category position
ax.text(x_position, 0, "42%")

# CORRECT — renders at the row matching this label
ax.text(x_position, category_label_string, "42%")
```

This applies to any manual `ax.text()` or `ax.annotate()` call on a categorical barh chart. The `plot_style.stacked_pct_hbar()` helper handles this correctly; the bug only appears in hand-written annotation code.
